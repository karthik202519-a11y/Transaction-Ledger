# Assumptions and decisions

1. The five-page assessment is API-first and allows any backend/database. React is the user-requested addition.
2. One generic currency/account unit with two decimal places is assumed. No FX or currency conversion exists. Positive values with more than two significant fractional digits are rejected; trailing zeros, such as 1.230, do not lose precision and are accepted.
3. API amount input accepts JSON numbers or decimal strings. Decimal strings are recommended. Booleans, null, NaN, infinity, zero and negative amounts are rejected. Responses always use decimal strings.
4. Each amount and balance is bounded at 9,999,999,999.99. Overflow is rejected before committing a balance change; database constraints enforce the same bound.
5. Account names are trimmed and required (1–120 characters); names need not be unique. UUIDs distinguish accounts. UUIDs and timestamps are generated by the server. Client-supplied initial balances, IDs, timestamps, or unknown input fields receive 422.
6. Descriptions are optional and at most 500 characters. References are trimmed, case-sensitive, and 1–120 characters. A duplicate gets HTTP 409 even if its amount or other fields differ. References may be reused on different accounts.
7. Each transfer uses the supplied reference on both participating accounts. If either account already has that reference, the entire transfer is rejected. Transfers to the same account are rejected. Transfer history is represented by linked debit/credit entries.
8. History uses `page=1`, `limit=10` by default. Limit is 1–100, page is 1–1,000,000. An empty result has `total_pages=0`; a page beyond the result returns no items. Sorting is creation timestamp descending, then an internal sequence descending for stable ties. Offset pagination can shift if new records are added between page requests; refresh returns to the latest view.
9. UTC timestamps are stored; the UI formats them in the browser's local timezone. The UI does not apply an exchange rate or a currency symbol.
10. Transaction immutability is enforced by the API surface. A database administrator can modify the database directly; tamper-proof storage was not required.
11. The account-list API is an additional UI convenience and returns all accounts. The assessment's pagination requirement applies to transaction history.
12. SQLite is a persistent file database, not an in-memory database. Startup creates missing tables but never resets data. Explicit transactions and foreign keys are enabled on every connection. No external database service is necessary.
13. No authentication, users/roles, registration, account deletion, direct balance adjustment, exports, interest calculations, or deployment was requested.
14. API and frontend listen only on the loopback interface by default. Vite is the local development server; a production bundle is also verified.
